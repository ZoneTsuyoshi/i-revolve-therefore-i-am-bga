## 目的

想い出カード（効果あり 42 種）、初期自我 8 枚、強化自我 5 枚、目標カード 7 枚、想起効果 13 分類、床アクション 12 室、精神分析ボーナス、周遊ボーナスのすべてについて、「いつ（タイミング）」「何を条件に」「何をするか」を機械可読な形に構造化し、006 の効果解決スタック（状態 70 / 71）でどう処理するかを決める。全カードを 1 枚ずつ割り当て表に載せ、同時に誘発する効果の解決順、コスト修正の重ね方、鍵の読み替え、目標カードの X の数え直し、FAQ のカード個別裁定の満たし方、単体テストで固定すべきケースまでを定める。

## スコープ

- 対象: 効果の構造化スキーマ（`EffectSpec`）、原子操作・イベント・修飾（コスト修正や鍵の読み替え）・条件の一覧、全カードの割り当て表、解決の仕組み（フェイズ別の発動点、同時誘発の順序、数値の計算式）、効果同士の相互作用、FAQ の満たし方、`Effects/` のクラス構成、007 への要求、単体テストの一覧、新たに見つかったルールの不明点
- 対象外: DB スキーマと通知の定義（→ 007。本書は必要な状態を「007 への要求」として列挙するだけ）、状態の遷移とフェイズの骨格（→ 006。本書は 006 の枠組みの上で効果を扱う）、画面と操作（→ 009）、英語の効果文の本文（→ 009 §8。実装タスクで起草）、コードと設定ファイル（この仕様書では作らない）

## 仕様

### 0. 記法と根拠

- 根拠の `001 §N`、`002 §N`、`003 §N`、`006 §N`、`009 §N` は各仕様書の節、`FAQ 行 N` は `faq.csv` のヘッダを 1 行目とした行番号、`Q-NN` は [rule-questions.md](../development/rule-questions.md) の質問番号、`R8-N`・`T8-N` は本書末尾の未確定事項（ルール・技術）の番号。
- 印: 【確定】= 承認済みの仕様書・作者回答・FAQ で決まっていること。【導出】= それらから論理的に導かれること（新しい裁定を含まない）。【提案】= 本書の設計案（実装方式の選択で、ルールの裁定ではない）。【暫定】= 材料が足りず仮置きしていること（未確定事項の番号を付ける）。作者の回答（2026-10-20）で、本書の【暫定】は全て【確定 R8-n（Q-xx）】になった。
- カード ID は 002 の識別子（`M001`〜`M099`、`F01`〜`F12`、`R1A`〜`R5`、`I01`〜`I08`、`E01`〜`E05`、`O001`〜`O007`）。想起効果の識別子（`DRAW_1` など）と効果の種類（`TURN_START` など）も 002 §3 のとおり。
- 本書が付ける ID は次の接頭辞。`OP-NN` = 原子操作、`MD-NN` = 修飾、`CD-NN` = 条件、`EV-NN` = イベント、`RC-NN` = 想起効果、`UT-NN` = 単体テスト。効果の ID は `カード ID.連番`（例: `M058.1`）。

### 1. 設計の全体像

#### 1.1 方針【提案】

効果の実装を次の 3 つの仕組みに分け、全てを「データ（`EffectSpec`）+ 共通エンジン」で表す。カードごとのクラスは作らない。

| 仕組み | 役割 | 例 | 解決の場所 |
| --- | --- | --- | --- |
| トリガー（`TRIGGER`） | イベントが起きたとき、条件を満たしていれば原子操作の列を実行する。frame をスタックに積んで 70 で解決する | M058（精神分析したとき）、M073〜M078（自己構成するたび）、E03（ターン開始時） | 70 `EffectResolve`（006 §7） |
| 修飾（`MODIFIER`） | 数値や選択肢を決める時点で問い合わせに答える。状態を変えず、frame を積まない | M060（レベル 2 の自己構成のエネルギー -1）、M059（心光の行使の軽減）、M094・M096（鍵の読み替え）、I03、I08 | 61・62・31 の検証と `getArgs` の計算（`Effects/Query/`） |
| 行動の定義（`ACTION`） | 想起効果・床アクション・精神分析ボーナス・周遊ボーナスのように、カードの持ち主の効果ではなく、場所やカードが定める行動。原子操作の列として書く | 想起 13 種、床 12 室、精神カード 9 枚、周遊ボーナス 4 種 | 70（frame）または 31 の適用 |

- 目標カード 7 枚は第 4 の種類（`OBJECTIVE`）で、条件と X の関数と得点表を持つ（§7.7）。frame を積まず、フリーアクション `actClaimObjective` とスコア計算が評価する。
- 原子操作（`OP`）は 26 種、制御構造は 4 種、イベントは 8 種、修飾は 11 種、条件は 13 種（§3〜§5）。想起効果・床・精神カードの行動も、効果文の効果も、同じ原子操作の組み合わせで表す。
- `Effects/` はフレームワークを直接呼ばず（003 §4.2）、ゲーム状態の読み取り（`GameView`）と書き込み（`GameMutator`）のインターフェースを通して動く。乱数は注入する。これで PHPUnit だけで全部品を検査できる。

#### 1.2 006 の枠組みとの対応【確定】

006 で決まっていること（変えない）と、本書が追加すること。

| 006 の内容 | 本書の扱い |
| --- | --- |
| 70 `EffectResolve` がスタックを先頭から解決。選択は 71、自己構成は 61、精神分析は 62、手札上限は 72（§7.2） | 同じ。frame の `kind` に `OP`（原子操作 1 つ）と `SPEC_RUN`（`EffectSpec` の操作列の実行。`step` で現在位置を持つ）を追加する。006 の `DRAW`・`GAIN_FIELD`・`LIGHT`・`DISCARD`・`SET_TURN_DISCOUNT` は `OP` の別名として扱う（名称の追加で、枠組みは変えない） |
| frame の項目 `owner`・`source`・`params`・`unit`・`cancel_to`・`origin`（§7.1） | 同じ。`origin` の値は §6.6、`unit` の境界は §6.9 で完成させる |
| `choice_kind` の主なもの 13 種（§7.4） | 完成させる（§6.4。14 種）。追加は `PICK_SPIRIT_BRANCH` のみ |
| `ORDER_EFFECTS` と、順序が結果に影響しないときの固定順（§7.5） | 「影響する」の判定を触る資源の衝突で定義する（§6.3） |
| 移動はまとめて確定（`actMove`）。経路中は選択の要る効果が無い（§5.1） | 経路中に働く効果は MD-04・MD-05・MD-06 と EV-04（I07）だけ。経路の確定後に EV-02・EV-03 のトリガーを積む（§6.2） |
| 想起 13 種の解決（§5.2）、床 12 室の frame 列（§5.3） | §7.3・§7.4 で原子操作に落とす |
| 手札上限の確認の単位 `unit`（§8） | 効果ごとの単位を §6.9 で割り当てる |
| 勝利判定の呼び出し位置（§9） | 呼び出す操作の一覧を §6.8 で定める |

### 2. 構造化スキーマ（`EffectSpec`）

#### 2.1 項目

1 つの効果 = 1 つの `EffectSpec`。1 枚のカードに複数の効果が印刷されている場合（I04 の 2 文など）は、効果ごとに分ける。

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `id` | 文字列 | `M058.1` のようにカード ID + 連番。想起効果は `RC-NN`、床は床 ID（`F01`）、精神カードは精神カード ID（`R2`）、目標は目標 ID |
| `source` | 文字列 | 出典のカード ID（想起効果は表向きにした想い出カードの ID が実行時に入る） |
| `mechanism` | 列挙 | `TRIGGER` / `MODIFIER` / `ACTION` / `OBJECTIVE` |
| `kind` | `EffectKind` | 002 §3.3。初期自我は §7.6 で割り当てる。想起効果・床・精神カードは `NONE` |
| `owner_scope` | 列挙 | 効果が働く人。`OWNER`（自己構成済みカード・自我カードの持ち主。反応するのはターンプレイヤーの手番中だけ。§4.1）、`ACTIVATOR`（想起効果の発動者）、`TURN_PLAYER`（想起効果のうちターンプレイヤーだけが使えるもの） |
| `hook` | イベントまたは問い合わせ | `TRIGGER` は EV-NN（複数可）、`MODIFIER` は修飾の ID（MD-NN） |
| `conditions` | 条件の配列 | CD-NN の AND（§5.2）。トリガーの収集時に評価し、解決の開始時にもう一度評価する（§6.3） |
| `ops` | 操作の列 | 原子操作（OP-NN）と制御構造（§3.2）。左から右へ順に実行する |
| `optional` | 真偽 | 「してもよい」を含む効果は真。解決の前に `CONFIRM_USE` を聞く（§6.4）。偽なら自動で実行する |
| `limit` | 列挙 | `PER_EVENT`（イベントのたびに）/ `ONCE_PER_TURN`（1 ターンに 1 回。使用済みを記録する）。既定は `PER_EVENT` |
| `unit` | 真偽 | この効果の解決が終わったとき、手札上限を確認する単位か（§6.9） |
| `touches` | 資源記号の集合 | 同時に誘発したときの衝突判定に使う（§6.3）。既定は操作の `touches` の和集合 |
| `params` | 連想配列 | 効果ごとの数値（`n`、`delta`、`table` など） |

- 【提案】`EffectSpec` は PHP 8.4 の値オブジェクトと `enum` で作り、`Material/EffectCatalog::all()`（静的メソッドが最初の呼び出しで 1 度だけ配列を組み立てる。クラス定数の初期化式では `new` が使えない可能性があるため）が、効果 ID をキーに返す。外部の JSON は持たない（カードごとの個別処理は無く、定義が短いため。003 §4.2 の `Material/` は 002 の生成物なので、手書きの `EffectCatalog` はその隣に別ファイルで置く）。
- 【確定】カード → 効果の対応は 002 の ID で引く（`EffectCatalog::forCard('M058')`）。英語の効果文（009 §8 の `texts.js`）はこの対応とは別の表で、キーが同じ（002 の ID）であることだけを検査する（§12 の UT-09）。

#### 2.2 例

M058 `観測前夜`（精神カードに進んだとき、そのカード上に心光が無ければ心光 +1）:

```text
id: M058.1   mechanism: TRIGGER   kind: ACTIVATED   owner_scope: OWNER
hook: EV-06 TIER_UP
conditions: CD-08(via = ANALYSIS_ACTION) AND CD-09(dest_had_light = false)
ops: [ OP-03 GAIN_LIGHT(n=1, origin=EFFECT) ]
optional: false   limit: PER_EVENT   unit: true(精神分析アクションの単位に含める)   touches: {L+}
```

M060 `あの日の残像`（レベル 2 の想い出カードを自己構成するとき、エネルギー -1）:

```text
id: M060.1   mechanism: MODIFIER   kind: CONSTANT   owner_scope: OWNER
hook: MD-01 COMPOSE_ENERGY_DELTA   params: { delta: -1 }
conditions: CD-13(composed_card.level = 2)
```

床 `F12 HEPHAESTUS`（自己構成アクション（エネルギー -1）/ 山札から 2 枚引く）:

```text
id: F12   mechanism: ACTION   kind: NONE
ops: [ CHOOSE_ONE( [ OP-10 COMPOSE(ctx=FLOOR, discount=1, optional=true) ],
                    [ OP-01 DRAW_DECK(n=2, origin=FLOOR) ] ) ]
```

### 3. 原子操作（OP、26 種）と制御構造（4 種）

#### 4.2 トリガーの収集

1. イベントが起きたとき、`EffectCatalog` から、そのイベントに反応する `TRIGGER` を持つ、ターンプレイヤーの自己構成済みカード・自我カードの効果を集める（手札のカードの効果は働かない。例外は `HELD` の M098 で、これは修飾）。
2. 各効果の `conditions` を評価する。満たすものだけが候補。`limit = ONCE_PER_TURN` で使用済みのものは除く。
3. 候補が 1 つ以上あれば、`SPEC_RUN` frame を積む（複数あれば §6.3 の順序づけ）。
4. 解決の開始時に条件をもう一度評価する。満たさなくなっていれば捨てる（例: 先に解決した効果で手札や場札が変わった）。解決の途中では再評価しない。
5. 自己構成済みカードの効果は、そのカードが自己構成された**後**から働く。ただし、自己構成したカード自身の ACTIVATED のトリガー（M073〜M078 が自身の自己構成に反応するか）は【確定 R8-3（Q-52）】で「反応しない」とする。

#### 6.2 移動フェイズ中の効果（`actMove` の検証と適用への追加）

006 §5.1 の検証と適用に、効果として次を加える。

1. **心光の行使の個数**: 移動フェイズの心光の行使を経路の順に数え、MD-04（MOVE）があれば n 回目の個数を表で決める（M063: 1・1・2・2・3、6 回目以降は n 個。FAQ 行 15）。表を使わない場合は n 個。
2. **鍵の判定**: 支払いに使う自己構成済みカード・手札の鍵が錠前に合うかを MD-05（MOVE）込みで判定する。M096 があれば `WILL` の鍵は万能鍵としても使える。
3. **MD-06（M064〜M066）**: このターン最初のレベル 2 の部屋への入室について、持っているカードの枚数だけ万能鍵（`src = EFFECT`、`card` = M064〜M066 のどれか）を支払いに使える。1 つの錠前に 1 つ。レベル 2 の部屋の錠前は 2 つなので、実際に使えるのは最大 2 つ（3 枚あっても 1 枚は余る）。
4. **途中で得た資源**【技術 T8-5】: 検証は経路を 1 部屋ずつ順にシミュレートする。周遊ボーナスで得た心光と万能移動鍵トークンは、その部屋の処理の後の部屋の支払いに使える（001 §6 はボーナスを「入室またはスキップのたびに獲得」とし、使用を禁じていない）。精神分析トークン・自己構成トークンも獲得するが、移動中は使えない（001 §5-1）。
5. **適用**: 経路を 1 部屋ずつ順に処理する。(a) 次の部屋がレベル 2 でスキップするなら、その部屋の周遊ボーナスを先に得る（次の部屋の支払いに使える）、(b) 入室する部屋の支払いを確定する、(c) 人格を移動し、入室数・入室済みの部屋の集合を更新する、(d) 入室した部屋がレベル 2 ならその周遊ボーナスを得る、(e) 最後の部屋でなければ EV-04 の判定（その部屋に他の人格がいて、I07 を持ち、このターン未使用なら、I07 の効果を使用済みにして 1 枚引く。手札上限の確認は移動フェイズ全体の後。Q-41）、(f) 勝利判定（12 部屋目の入室、または心光・トークンの増加による断片の結集。§6.8）。
6. **確定後**: `MOVE_ENDED`（EV-02）と `PERSONA_STOPPED`（EV-03、`via = MOVE`）のトリガーを収集して `resume = 40` で 70 へ。EV-02 のペイロードは、使った万能移動鍵トークンの数（I06 の判定）、支払いで使った鍵の種類（M061 の判定。FAQ 行 19・20）、入室数（M067・M069 の判定）、止まった部屋にいる他の人格。
7. 【導出】M067・M069 は経路の確定後（`MOVE_ENDED`）に判定する（006 §5.1 の 5）。移動中に 4 部屋目で得た心光を、同じ移動の以降の支払いに使うことはできない【確定 R8-13（Q-62）】。想起効果の移動で 4 部屋に達する場合は、その移動の後の `PERSONA_STOPPED` で判定する（FAQ 行 23）。

#### 6.3 同時に誘発した効果の順序

##### 6.3.1 規則

1. 同じイベントで複数の効果が誘発したら、同じ持ち主（= ターンプレイヤー。§4.1）の効果を 1 つの集合にまとめる。
2. 集合の効果の「触る資源」（下表）を比べ、**衝突する効果の対が 1 つでもあれば**、`ORDER_EFFECTS`（ターンプレイヤーが「次に解決する効果」を 1 つずつ選ぶ。Q-29、FAQ 行 24・26）を聞く。
3. 衝突する対が無ければ、結果が順序によらないので、**固定順**で自動に解決する（006 §7.5）。固定順は、そのカード自身の即時効果（EV-05 のとき）、次に効果 ID の昇順。
4. 「してもよい」の効果は、解決の番が来たところで `CONFIRM_USE` を聞く（順序を選ぶときに、使わないことを先に決める必要はない）。
5. 同一の定義の効果（操作列と条件が同じ。M052 / M053 / M054、M055 / M056 / M057、M064 / M065 / M066）は互いに交換可能なので、対にしても衝突とみなさない。

#### 6.5 自己構成・精神分析・心光の行使の計算

##### 6.5.1 自己構成エネルギー

61 の `actCompose` が検証する式。【確定】FAQ 行 18: エネルギーは 0 未満にならない（0 への切り上げは最後に 1 回）。

```text
cardEnergy = max(0, card.energy + Σ MD-02(card))          # 手札の M098 だけ変わる。I03 と OP-09 の比較もこの値
discount   = ctx.discount                                  # HEPHAESTUS の分岐の 1、床アクションの代替（RC-10・RC-11）の割引 1
           + turn_compose_discount                         # POSEIDON（OP-22）
           + next_compose_discount                         # 自己構成アクション（PHASE / TOKEN / FLOOR）のときだけ。完了時に全て消費
           + Σ MD-01(conditions を満たすもの)               # M060、M077、M068、E01
           + tap_count                                     # MD-07（M095）で横向きにした枚数
need       = max(0, cardEnergy - discount)
paid       = Σ(捨てた手札のレベル) + Σ(心光 n 回目の個数の逆算。MD-04 COMPOSE)
valid      = paid >= need                                  # 過払い可（Q-22）。余りは失われる
```

- 心光で n 回目の行使に払う個数は、既定では n 個、MD-04 があれば 1・1・2・2・3 個（6 回目からは n 個。FAQ 行 15・17）。エネルギー（または鍵）を `m` 個分買うときの心光の総数は、1 回目から `m` 回目までの個数の和（`m` = 1〜6 で、既定は 1・3・6・10・15・21、M070 は 1・2・4・6・9・15）。アクションごとに n をリセットする（FAQ 行 16）。
- 軽減は加算で重なる（順序は関係しない）。複数の軽減が同時に働くので、カード効果どうしの重ね方の問題は起きない（各軽減の出典は別々のカードで、同名の自己構成は 1 枚だけ。001 §9-1）。
- MD-07（M095）は `tap_count` を増やす。過剰な横向き（`need` を超える枚数）は入力エラーにする【技術 T8-10】。
- MD-09（I03）の代替は `need` を使わない（エネルギーなし）。
- 完了時（カードが自己構成済みになったとき）: `next_compose_discount` を 0 にする（自己構成アクションの文脈のとき）、`compose_actions_done` を 1 増やす（同）、EV-05 を起こす。`actCancel` されたアクションでは何も消費しない。

##### 6.5.2 文脈 `ctx` ごとの規則（OP-10）

| `ctx` | 呼び出し元 | エネルギー | レベル制限 | `next_compose_discount` を消費 / `compose_actions_done` に数える | MD-01 | MD-07 | MD-08 | MD-09 | 行わない選択 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `PHASE` | 60 の `actStartCompose` | 通常 | なし | 消費する / 数える | 適用 | 可 | 可 | 可 | 可（60 に戻る） |
| `TOKEN` | 60 の `actUseComposeToken` | 通常 | なし | 消費する / 数える | 適用 | 可 | 可 | 可 | 可（トークンは消費されていない） |
| `FLOOR` | POSEIDON・HEPHAESTUS・代替 | 通常。`discount` を足す | なし | 消費する / 数える | 適用 | 可 | 可 | 可 | 可（51 に戻る。006 §5.3） |
| `BONUS_LV1` | R2 | 0 | レベル 1 | 消費しない / 数えない【確定 R8-6・R8-7（Q-55・Q-56）】 | 無関係 | 不要 | 可（FAQ 行 38） | 不可 | 可（「してもよい」） |

- 全ての文脈で同名カードの制限は適用される（FAQ 行 21、001 §9-1）。自己構成できるカードが無ければ、その `COMPOSE` は何もせずに終わる。
- MD-09（I03）は、エネルギーを払う文脈（`PHASE`、`TOKEN`、`FLOOR`）でのみ使える。無料の文脈では通常の自己構成が無料なので、代替する利益が無い【技術判断。損失なし】。

##### 6.5.3 精神分析コスト

```text
unitsNeeded = card.cost の鍵の集合（例: R4 = 知恵 2・感情 2・意志 2）
reduction   = Σ MD-03(E02) + ctx.discount（代替の想起効果の割引 0 または 1）
needUnits   = unitsNeeded から reduction 個の鍵をプレイヤーが選んで取り除いた残り（0 個を下限）  # 【技術 T8-3】
payment     = 自己構成済みカード（横向きにする。鍵は複数同時に使える）
            + 手札（捨てる。MD-10 があれば床の下へ）
            + 心光（n 回目の個数は MD-04 ANALYSIS）
valid       = 各 needUnits の鍵に、MD-05(ANALYSIS) 込みで合う鍵（または万能鍵）を 1 つずつ割り当てられる
```

- 万能移動鍵トークンは使えない（001 §10-2）。同じターンに移動で横向きにしたカードは使えない（横向きのまま。クリーンアップ a まで）。
- M094 の読み替えは `WISDOM` → `WILD`（精神分析アクションの間）。この間、知恵鍵は知恵としても万能としても使える（FAQ 行 20 と同じ解釈）。

##### 6.5.4 鍵の読み替え（`KEY_VIEW`）

- 【確定】読み替えは「元の種類としても万能鍵としても見てよい」（FAQ 行 20）。万能鍵は他の全ての種類の代わりになるので、実質は「その鍵はどの錠前・コストにも使える」。
- 文脈【技術 T8-6】: 31 の `actMove` の検証と適用は `MOVE`（M096 が働く）、62 の `actAnalyze` と精神分析の支払いは `ANALYSIS`（M094 が働く）。それ以外の状態では読み替えは無い。
- 目標カード O007 の条件「万能鍵が存在する」の判定は、その時点の文脈の読み替えを含めて行う（FAQ 行 29）。したがって、M096 を持つ人は 31 の中（フリーアクションとして `actClaimObjective` を呼べる。006 §6.2）で、M094 を持つ人は 62 の中で O007 を獲得できる。X（セットの数）、O003 の最多鍵の本数、`COUNT_COMPOSED_KEYS` には読み替えを適用しない【確定 R8-19（Q-68）】。
- M061 の判定（CD-02）は読み替えと独立で、カードに印刷された鍵の種類で数える（FAQ 行 19・20。§5.2）。

#### 6.6 `origin` の値と反応

frame の `origin`（006 §7.1）は、反応する効果が「何による獲得か」を判定するための印。

| `origin` | 付ける操作 | 反応する効果 |
| --- | --- | --- |
| `FLOOR` | 床アクションの要素として直接列挙された OP-01 / OP-02 / OP-03 | M085〜M087（EV-08）。周遊ボーナスの心光（POSEIDON の足跡）、精神カード上の心光、床アクションの代替先の精神分析・自己構成の中身には付けない（FAQ 行 27） |
| `SPIRIT_CARD` | OP-05（精神カード上の心光） | I02（EV-07）。M085 には反応させない（FAQ 行 27） |
| `TOUR` | 周遊ボーナスの OP-03 / OP-04 | なし（O005 の獲得数には数える） |
| `RECALL` | 想起効果の OP | なし |
| `BONUS` | 精神分析ボーナスの OP-01 | なし（M086 は床の効果だけ） |
| `EFFECT` | カード効果（M058、M076、M079 など）の OP | なし（I02 は反応しない。FAQ 行 11） |

- 【技術 T8-9】`origin` は子の frame に**伝播させない**。床アクションの `COMPOSE` / `ANALYZE` の frame が積む子 frame（精神分析ボーナスの引き、精神カード上の心光、自己構成のトリガー）は、独自の `origin` を持つ。

#### 11.1 クラス構成【提案】

```text
src/modules/php/
├── Material/                          # 不変のデータ（003 §4.2。002 の生成物と、手書きの効果定義）
│   ├── EffectSpec.php                 # 効果の定義（値オブジェクト。§2.1）

    ├── EffectEngine.php               # イベント → トリガーの収集 → frame（70 が呼ぶ）
    ├── Trigger/  TriggerCollector.php  ConflictResolver.php  FixedOrder.php
```
