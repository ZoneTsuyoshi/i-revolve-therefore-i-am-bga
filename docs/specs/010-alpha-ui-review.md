## 目的

姉妹プロジェクト（MINIMUM JOURNEY の BGA 実装）が BGA の Public Alpha 審査で「UI/UX が公開アルファに達していない」という指摘を受けた（原文は下の「姉妹の指摘（原文）」）。**このゲームはまだ審査を受けていない。** 指摘のほぼすべてがこのゲームにも当てはまるため、審査に出す前に先回りして直す。指摘を 8 項目（R1〜R8）に分け、BGA 公式の UX ガイドラインと現在の実装に照らして原因を特定し、直し方を決める。承認後、別の PR（U-11〜U-16）で実装し、作者が Studio で確認してから審査に出す。

009 の画面設計（§2.4・§3.10・§3.11・§4・§6・§12）の一部を、この仕様書で変更する。

## スコープ

- 対象: Action Bar のボタン、画面構成（配置・カード幅の決め方）、情報の置き場所（パネルと領域）、プレイヤーの領域、見た目（卓上の表現）、背景、レスポンシブ、アクセシビリティ、検証方法（ローカルのプレビュー環境）、実装の分け方。
- 対象外: ルール（001。ルールの不明点は出ていない）、サーバー（PHP）の変更（不要の見込み）、カード画像・スプライト（009 §10・§11）、拡大表示とツールチップの仕組み（009 §7。クリックで拡大を開かない方針も維持）、メタ画像（009 §14。U-9）、チュートリアル。

### 2. Action Bar（A.2・B.2・B.3・C.3。R1）

#### 2.1 色の規則

**【確認】** C.3 は色を「BGA 共通の言語。必須」とする（青 = 進む・確定、赤 = 取消・やめる・止める・出る、白 = 任意・脇の操作、灰 = 無効・完了・使えない）。ゲーム固有の意味で青・赤・灰を再定義しない、テーマに合わせてボタンを着色しない、とも書かれている（UxPdf C.3）。

| 色 | `color` | 使う場面（このゲーム） |
| --- | --- | --- |
| 青 | `primary` | 進める・確定する主な操作（Construct a card、Confirm、Confirm move、Stay（移動できないとき）、Use / Move（効果を使う・移動する）、Claim goal、Discard for Psychic Light、床アクションの選択） |
| 赤 | `alert` | 取り消す・戻る・止める・やめる（Cancel、Undo last room、End construct phase。**End construct phase は「このフェイズの自己構成を止める」ので赤。** 現状の色のまま） |
| 白 | `secondary` | 任意・脇の操作（Skip、Do not use、トークンの使用、Swap with Architect、Choose extra cards、Change card / destination） |
| 灰 | `disabled: true` | 今は使えない（支払いが足りない Confirm など）。理由をツールチップに出す（D.1「失敗は理由を言う」） |

- 色だけに頼らず、ボタンは必ず文字ラベルを付ける（E.1）。
- B.2: 「今は使えないが存在する操作」は灰で出し、**この場面で関係のない操作は出さない**。使えない [Claim goal] を常に出すのと、トークン 0 個のときの [Use … token (0)] をやめる（§2.3）。

#### 2.2 並びと個数

**【確認】** A.2: 主な操作を中央に、二次・無効の操作をその隣に、取り消し系を右に離して置く。取り消しが主な操作と競合して見えないようにする。ボタンは「最大 4 個＋文脈」（タイトルが文脈）。BGA の組み込みボタンの隣に独自のボタンを寄せない。B.3: Undo / Reset / Confirm を重ねない。

- 青 → 白 → 赤 の順に追加し、取り消し系（赤）は右端にする。
- 1 つの状態で出すボタンは **4 個まで**を目標にする。超えていた状態（自己構成の支払い 9、精神分析の支払い 8、移動 7、自己構成フェイズ 6）は、§2.3・§2.4 で数量ボタンとフリーアクションを部品へ移し、Reset を廃止して収める。
- 例外: 「目標を獲得する」ボタン（§2.4）は、獲得できる目標を選んだ間だけ出る。自己構成フェイズでは一時的に 5 個になる。
- 効果の順番の選択（`EffectChoice` の `ORDER_EFFECTS`。`ChoiceState.js:208-216`）は、同時に処理する効果の数だけ出る（人数と手札の想起効果で増える）。4 個を超えうるが、選択肢そのものなので例外とする。

#### 3.1 前提と記号

- 記号: `Wc` = `#ir-root` の幅（`Layout.js` が測る）、`Hv` = 見える高さ（`window.innerHeight` から、盤面より上にある BGA のトップバー・ステータスバーの高さを引いた値。実装時に `root.getBoundingClientRect().top` などで測る。**【推定】** 1920 × 1080 の画面で、ブラウザの上部を除く約 950px からトップバーとステータスバーの約 140px を引いて約 810px）、`g` = 隙間（wide 以上は 8、narrow は 6）、`W` = 部屋（床カード）の幅、`w` = 想い出カードの幅 = `min(128, 0.6W)`、`c` = 横長カードの幅 = `0.7W`（narrow は 009 §2.4 のまま）、`wp` = プレイヤーの領域のカードの幅。

#### 3.3 配置とカード幅の決め方【提案】

数値は U-13 のプレビューで調整してよい基準値。

1. **幅から求める W**: 009 §2.4 と同じ（`wide` 系は `W_w = min(213, floor((Wc − 5g − 16) / 6.1))`、`medium` は `min(213, floor((Wc − 3g) / 4))`）。
2. **高さから求める W**: `W_h = floor((Hv − 4g) / 4.906)`。デスクトップ・タブレットの配置（`xl`・`wide`・`medium`）では、環と山札の行が見える高さに収まるよう、`W = min(W_w, max(W_h, 150))` にする（下限 150。それより小さくせず、収まらない分は少し縦にスクロールする）。`narrow` は高さで抑えない（縦に積むため）。
3. **配置の判定**（上から順に、最初に満たしたものを使う）:

| 配置 | 条件 |
| --- | --- |
| `xl` | `Wc ≥ 6.1 × W_x + 7g + P_w`。ここで `W_x = min(213, max(W_h, 150))`、`P_w = 4 × wp + 3g + 22`（プレイヤーの列の幅。`wp = 128` で 558）。**実装での読み替え: 22 → 28（`wp = 128` で 564）。実際の領域の枠と余白（領域の枠 1 + 余白 6、手札・自己構成済みのマットの枠 1 + 余白 6 を両側で 28）に合わせた。`layout-math.js` の `AREA_CHROME` と CSS の `--ir-area-chrome` で一致させている** |
| `wide` | `W_w ≥ 150`（`Wc ≥ 971`。現行の `WIDE_MIN = 1100` を式から導く値に置き換える） |
| `medium` | `Wc ≥ 600`（現行どおり） |
| `narrow` | それ以外（`Wc` の下限 360。現行どおり） |

- **プレイヤーの領域のカード幅 `wp`**【提案】: 手札・自己構成済みのカードは主な操作の場なので、環の幅 `W` から切り離し、`wp = min(128, max(floor(0.6W), 104))` とする（`xl` は 128）。環の中央の場札と山札は従来どおり `w = min(128, 0.6W)`。現状は `--ir-w` ひとつがすべてのカードに効く（`css:657-667`）ので、`--ir-wp` の変数と `.ir-stock-mp` のクラスを足す。bga-cards の寸法変数を `!important` で上書きする既存の流儀に合わせる。必要がなければ（プレビューで `w` のままで十分なら）導入しない → 未確定事項 No.2。
- 実装: `layout-math.js` の `computeSizes` に `viewHeight` を引数として足し、`layoutOf` を上の判定に置き換える。`Layout.js` は `window.innerHeight` と `#ir-root` の上端から `Hv` を求め、`ResizeObserver` と `resize` の変更で再計算する。`data-layout` に `xl` を足し、`placeFloating`（`board/Board.js:211`）は `xl` を `wide` と同じ扱いにする。ブラウザのズーム・画面の回転・ウィンドウの変更で再計算する。縦スクロールバーの出入りで配置が行き来しないよう、大きい配置・大きいカード幅へ変えるのは、幅が 24px 狭くても同じ結果になるときだけにする（姉妹 013 §13 の教訓）。

#### 7.3 画像を使う場合の生成と扱い（案 A または C を選んだときだけ）

### 13. 実装で確かめる点（姉妹 013 §13 の教訓の読み替え）

- 配置が切り替わる境目で、`placeFloating`（`board/Board.js:211`）が `ir-piles` と `ir-open` を付け替える（作り直さない。Stock が壊れない）。`xl` の追加でこの付け替えが変わらないことを確かめる。
